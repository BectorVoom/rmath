# Speed and precision optimisation plan, cycle 2

Status: executed
Prepared: 2026-08-25
Scope: the optimisation cycle after [`OPTIMIZATION_PLAN.md`](OPTIMIZATION_PLAN.md)
(2026-08-20), whose workstreams A–G were executed in commits `4eee3e3` and
`e5f1f22`. This plan starts from the measured state those commits produced
(`bench_results/final_native.csv`, AMD Ryzen AI 7 350 / Zen 5 / AVX-512,
glibc 2.43, `-C target-cpu=native`).

## 1. Goal

Same Pareto rule as last cycle: an optimisation counts only when it moves a
measured speed/precision frontier without weakening a contract. This cycle's
specific outcomes, in priority order:

1. **Re-verify and reconcile** the previous cycle's headline claims before
   building on them — three of them are currently stated inconsistently
   across code, tests, README, and commit messages (§4).
2. **Close the remaining below-parity `BitExact` rows**: `acos` 0.76x,
   `asin` 0.81x, `acosh` 0.83x, `log1p` 1.05x.
3. **Narrow the exact-vs-fast gap where it is anomalous**: `exp2` exact
   1.74x against `exp`'s 3.20x; `pow` exact 1.46x.
4. **Make the benchmark numbers corpus-honest**: at least one row (`atan`
   exact 9.04x) is now dominated by a band-coherence bypass that the default
   corpus happens to trigger almost always (§5.4).
5. **Pin the table generator's upstream sources** — the reproducibility gap
   `ROADMAP.md` §6a explicitly left as a follow-on.

## 2. Contracts that must not change

Carried over verbatim from the last cycle; they remain hard:

- `BitExact` matches the platform bit-for-bit, including signed zero,
  infinities, NaN payloads, and FMA placement read from disassembly — not
  source-level equivalence.
- Every `Fast` bound is asserted in `tests/accuracy.rs`, quoted identically
  in the kernel doc and README, and may only be tightened after a measured
  campaign (30M+ samples for `f64`, exhaustive for `f32`).
- `FullRange` is correct for all inputs; `Finite` skips checks only inside
  its documented domain.
- Tables and coefficients are generated by `tools/`, never transcribed.
- Rare lanes are repaired by `reference/` through `patch_lanes`; the vector
  main path never owns the hard cases.
- Acceptance evidence is end-to-end (`examples/bench.rs` rows), not
  microbenchmarks.
- One extra rule this cycle, learned from the CORE-MATH ports (§5.1): a
  kernel whose acceptance test is `lb == ub` (correctly-rounded fast path
  with rounding-boundary rejection) is bit-exact **only because** this
  host's glibc 2.43 ships the same correctly-rounded algorithm. That
  equivalence is a property of the platform version, not of the algorithm —
  every such kernel must keep its full-corpus bit-exact test so a platform
  drift fails loudly.

## 4. Phase 0 — verify before building (P0, small, blocks everything)

The last cycle landed six workstreams in two large commits with claims that
now disagree between surfaces. Nothing in §5 onward starts until each claim
below is re-measured on this machine and every surface (kernel doc, test
assertion + its comment, README, ROADMAP) quotes the same number.

1. **Tree hygiene.** Commit the rustfmt churn as its own commit; commit the
   bench.rs plumbing separately. Confirm `cargo test --release` (default and
   `--no-default-features`), clippy, and rustdoc are clean at that point.
2. **`tgamma` ≤ 1 ulp claim.** Run
   `RMATH_SCAN_N=100000000 cargo test --release --test ulp_scan scan_gamma -- --ignored --nocapture`.
   Record worst input and ulp. If confirmed: update README (§"tgamma" caveat
   currently quoting 512–513), ROADMAP's C2 entry, and close the old plan's
   Workstream F with the measured number. If refuted: the accuracy test's
   1e-14 relative assertions are at risk of being corpus-lucky — treat the
   direct large-argument algorithm as still open and re-scope it from the
   old plan's Workstream F.
3. **`cbrt` `Fast` bound.** Run `scan_cbrt` at 500M with the extreme-magnitude
   corpus. The asserted 4 requires a measured worst of ≤ 2–3 with the crate's
   customary headroom; the stale doc comment (8) and the commit claims (1)
   cannot both be right. Fix the doc comment, README, and — if the measured
   worst is actually above 4 — **the assertion**, treating that as a released
   regression to root-cause (the `e5f1f22` "FMA residual compensation" change
   to `src/kernels/double/cbrt.rs` is the suspect surface, and the previous
   cycle's own analysis explains why ~8 ulp was believed structural: no wider
   type to run Newton in).
4. **`asinh`/`acosh` corpus completeness.** Their exact cores branch on raw
   bit thresholds (`0x3ff1e83e425aee63`, `0x405bf00000000000`,
   `0x4087100000000000`, `0x40e0100000000000`, `0x41ea000000000000`, and the
   asinh equivalents). Confirm `tests/bit_exact.rs` includes each threshold
   ±2 representable neighbours at every width, plus the `lb != ub` rejection
   path (inputs constructed to land within `eps` of a rounding boundary, so
   the reference fallback is actually exercised). Add what is missing.
5. **Fresh baseline.** Re-run `tools/bench_matrix.py` for the §7 protocol
   grid, commit the manifest. This is the "before" for every §5/§6 change.
   Given this machine's recorded noise (identical-binary swings of 20–70% on
   cheap rows), every accept/reject below uses alternating-run medians via
   `tools/bench_diff.py`, never single runs.
6. **Pin `gen_tables.py` upstreams.** Every fetched source (glibc files and
   ARM optimized-routines) gets a pinned commit hash asserted at fetch time.
   The unpinned `master` fetch already produced a silent full-table rewrite
   once (ROADMAP §6a, "upstream-drift hazard"); this closes it. Acceptance:
   regeneration is byte-identical from a clean checkout, and a deliberately
   wrong pin fails loudly.

Deliverable: a tagged, reproducible baseline whose documentation agrees with
its measurements everywhere.

## 5. Speed workstreams

### 5.1 S1: vectorise the `acosh` (then `asinh`) exact band structure — P1, medium

Today both exact cores are scalar functions called per lane
(`hyper.rs::bit_exact` is literally a `for i in 0..V::LANES` loop over
`scalar`). `asinh` still clears 1.24x because its scalar core beats glibc's;
`acosh` does not (0.83x plain, 1.03x `+Finite`). The structure is the same
five-band shape every other ported kernel vectorises: bands selected by bit
thresholds, a shared log-table tail (`t::B`/`R1`/`R2`/`L1`/`L2`), and a
per-lane-only table lookup.

Plan, `acosh` first because it is the one below parity:

1. Vectorise the two polynomial bands (`1/(x*x)` series) and the common
   log-tail arithmetic; evaluate bands unconditionally and blend with
   `V::select`, per the crate's standard idiom (`trig.rs`, `invtrig.rs`).
2. Keep the `B[i]`-indexed lookup per-lane (the gather lesson from A5 —
   do not reach for `gather_bits` first; the per-lane idiom won on this
   machine every time the slot count was small).
3. Turn the `lb == ub` acceptance into a lane mask; route rejected lanes
   through `patch_lanes` to `reference::acosh`. The rejection rate is tiny
   by construction (only rounding-boundary straddles), so this is the
   sparse-repair case the shared helpers are already tuned for.
4. Same treatment for `asinh` only if `acosh`'s end-to-end row confirms the
   approach (it starts from 1.24x, so its bar is higher and the win smaller).

Acceptance: `acosh` exact ≥ 1.25x (from 0.83x), zero bit mismatches on the
§4.4-hardened corpus at every width, `Fast` rows within 3%. Record a negative
result in the module doc if the blend overhead eats the win — that outcome is
plausible because unconditional evaluation pays for all five bands.

### 5.2 S2: `asin`/`acos` exact parity — P2, medium, explicitly experimental

Still 0.76–0.81x. Two experiments are already recorded as negative: the
AVX-512/AVX2 hardware gather (rolled out, measured, rolled back — ROADMAP
§3 A5) and, per the old plan's Workstream E, the uniform-band coherent
bypass landed in `e5f1f22` but visibly did not move these rows on the
default corpus (`unitargs` spread across all bands, so vectors are rarely
uniform). Do not repeat either. The hypotheses that remain genuinely untried:

1. **Shrink the gathered row.** The 13-slot `asncs_row` gather is ~90% of
   the exact path's cost (measured last cycle: removing it jumps the row to
   5.9x). The 2568-entry `asncs.x` table packs rows of degree 5–8 plus
   offsets; splitting it at generation time into per-degree tables (a
   `gen_tables.py` change, provenance preserved) lets a lane gather only
   `degree + 2` slots instead of 13. Expected value: up to ~30–40% of the
   gather cost for the low-degree bands that dominate `[-1, 1]` inputs.
2. **Batch the gather across the row dimension.** Load each lane's 13
   contiguous slots with two `f64x8` vector loads from the row base instead
   of 13 scalar loads, then transpose in-register only if profitable at
   width 8. This is a contiguous load per lane, not a gather — a different
   instruction budget from A5's `vpgatherqq`.
3. If neither clears the bar, **accept and close**: document 0.76–0.85x as
   the permanent cost of bit-exactness for these two on this
   microarchitecture, point users at `Fast` (9.3–10.6x, ≤ 4 ulp asserted),
   and stop re-opening the question each cycle.

Acceptance: exact ≥ 1.0x on the default corpus with bits unchanged, other
rows within 3%; otherwise outcome 3 with the measurement recorded.

### 5.3 S3: `log1p` exact (1.05x) — P2, small/medium

The kernel already evaluates its polynomial tail vectorially; the per-lane
part is the branchy reduction (`k`, `c`, `f`, `hu` extraction —
`logx.rs::bit_exact`'s lane loop). The reduction's branches are all
bit-threshold selects on `hx`, the same shape `ln`'s vectorised reduction
already handles without a lane loop. Prototype: compute `1 + x`'s exponent
split and the `c` compensation arithmetically per vector (the `hu < 0x6a09e`
renormalisation is a two-way select), leaving per-lane work only where an
integer shift is genuinely required (the known `Simd` primitive gap).
Acceptance: ≥ 1.25x exact (from 1.05x), bits unchanged on `corpus_log1p` at
every width. If the tiny/`hu==0`/`k==0` special-web resists vectorisation,
record why and stop — `Fast` at 11.5x already serves speed-seeking users.

### 5.4 S4: benchmark corpus honesty for the coherent bypass — P1, small

`atan` exact reads 9.04x because the default corpus (`±1e4` uniform) lands
nearly every lane in the single `[16, 5.8e15)` band, so the `e5f1f22`
uniform-band bypass fires almost always. That is a legitimate result *for
that corpus* but the table presents it as the row's one number, exactly the
"win on one corpus presented as universal" failure the old plan warned
about.

1. Report `atan`/`asin`/`acos` (and any other kernel with a coherence
   bypass) on **both** the default and the `in-domain` corpora in the README
   table, or annotate the row with its corpus.
2. Add a bench assertion (or `bench_matrix.py` check) that flags any row
   where exact > fast — that inversion is always either a corpus artifact
   or a policy wiring bug, and should demand an explanation rather than
   pass silently.
3. Measure the bypass's cost on the *incoherent* corpus (the uniform-band
   test is paid per vector even when it never hits). If it costs > 3% there,
   make it width- or corpus-gated, or reconsider.

### 5.5 S5: `exp2`/`pow` exact gap — P3, small to diagnose, unknown to fix

`exp2` exact 1.74x vs `exp` 3.20x is unexplained; they share the table
family and schedule shape. `pow` exact at 1.46x has a newly plausible
contributor: `pow_exp`'s per-lane loop gained two extra compares and
branches per lane (`k >= 1023*128` / `k >= 1024*128` big-scale handling)
when it was extended for `tgamma` in `4eee3e3` — cost `pow` now pays on
every call though its own `bad`-mask preconditions may make the branches
unreachable there. Diagnose first, fix second:

1. Profile both rows (perf annotate on the bench binary) and attribute the
   `exp2` gap; do not guess.
2. If the big-scale branches show up in `pow`: hoist them behind a
   whole-vector `kd.gt_mask(...)` guard (the `tgamma` dual-compute pattern)
   or split `pow_exp` into the `pow`-facing narrow version and the
   `tgamma`-facing wide one. Bits must not change for either caller —
   both have full-corpus exactness tests to hold them.

Acceptance: an explanation on record for `exp2`, and any landed change
≥ 5% on its row (shared-primitive threshold) with all exactness suites green.

### 5.6 S6: f32 `Fast` exponentials — P3, small, optional

`expf`/`exp2f`/`exp10f` `Fast` ≈ exact (2.0–2.4x both): the fast path adds
nothing because the exact port is already vector and cheap. Either document
this as the `erf`-style considered stance ("no cheaper approximation worth
having") in each module doc, or prototype a genuinely cheaper native path
(single polynomial, no table) and accept only at ≥ 1.5x over exact with a
≤ 4 ulp exhaustive bound. The documentation outcome is fully acceptable;
what is not acceptable is the current silent ambiguity.

### 6.1 P1: reconcile and re-assert (part of Phase 0, listed for visibility)

`tgamma` (§4.2) and `cbrt` (§4.3) are verification items, but each has a
follow-on precision decision:

- If `tgamma` confirms ≤ 1 ulp: also re-scan the negative half-line
  (reflection formula composes `sin_pi` and the positive path — its error

- If `cbrt`'s honest worst is 8: either revert the bound to 16-with-headroom
  and keep the speed, or spend the double-double final-step cost the last
  cycle priced and declined. That is an explicit Pareto decision to record,
  not a silent choice.

### 6.2 P2: `pow` extreme-exponent corpus, 8 asserted / 5 measured — P3

Unchanged from the old plan's Workstream G. The amplification near
`|y·log2(x)| ≈ 1020` is structural; a fix means carrying the reduction into
`pow_exp` with one more double-double term. Attempt only after S5's
profiling, since the same code moves; accept only with a strictly lower
asserted bound at ≤ 3% throughput cost on both `pow` rows.

### 6.3 P3: 100M-sample re-sweep of anything touched — standing rule

Every kernel §5 touches re-runs its `ulp_scan` entry at 30M (100M when a
bound moves) before its bench comparison is accepted. The scan entries all
exist (`scan_inverse_hyperbolic`, `scan_inverse_trig`, `scan_gamma`,
`scan_cbrt`, `scan_pow`, `scan_exponentials`); no new harness work needed.

## 7. Measurement protocol

Unchanged from the previous plan (§4 there), with two amendments:

- **Noise floor**: this machine has shown identical-binary swings of 20–70%
  on cheap rows. All gates use `tools/bench_matrix.py` runs with the
  landed warm-up + median-of-10 statistic, alternating before/after builds,
  and `tools/bench_diff.py --threshold 0.03` on ns/element as well as
  speedup. A change whose claimed win is inside the row's measured
  dispersion is not accepted on this machine — either quiet the measurement
  (idle machine, pinned frequency) or find a bigger win.
- **Corpus duality**: any kernel with a data-dependent bypass (currently the
  invtrig coherent path; S1 adds the `lb == ub` rejection) is gated on both
  the default and the adversarial corpus for its bypass (incoherent for
  coherence bypasses; rounding-boundary-dense for `lb == ub` paths).

Acceptance thresholds also carry over: ≥ 10% on the targeted row (≥ 5% for a
shared primitive improving several rows), no unrelated row worse than 3%,
correctness suites green at every width, `f32` changes exhaustive.

## 9. Explicit non-goals for this cycle

- Re-running the hardware-gather rollout on this CPU (twice measured, twice
  negative). S2's experiments are specifically the ones that are *not* that.
- `jn`/`yn`/f32-Bessel `BitExact` ports (README's standing decision).
- Native `erfcf` `Fast` (measured and killed last cycle; module doc records it).
- Chasing `sqrt`/`sqrtf`/`round`/`trunc` rows — hardware-instruction bound.
- f32 exact rows for `sinf`/`cosf`/`tanf`/`cbrtf`/`tanhf`: parity delegation
  is the design (platform is not correctly rounded, so there is nothing
  stronger to be exact *to*).
- Weakening any published bound to move a bench number — a bound change in
  either direction is a Phase-0-style reconciliation with a scan behind it.
