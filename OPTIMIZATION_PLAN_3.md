## 1. Goal

Same Pareto rule as the last two cycles: an optimisation counts only when it
moves a measured speed/precision frontier without weakening a contract. This
cycle's specific outcomes, in priority order:

1. **Finish cycle 2's bookkeeping** before building on it. Three closure
   items from that plan never landed: the `exp2` gap explanation (its S5
   acceptance was "an explanation on record" — none exists in `exp.rs`,
   ROADMAP, or any commit body), the S6 f32-exponential stance, and the
   plan document itself (`OPTIMIZATION_PLAN_2.md` is still untracked).
   README's headline tables are also now stale against the ROADMAP and the
   fresh matrix (§4).
2. **Close or explain the Exact-group large-buffer deficit**: `floor` 0.66x,
   `round` 0.68x, `trunc` 0.64x, `sqrt` 0.73x under `BitExact` at 1 M
   elements — functions whose vector body is one instruction, at parity at
   4096 elements, and *below* the scalar loop only in the memory-bound
   regime (§5.2). README currently claims 1.00x for `sqrt`.
3. **Explain the `exp2` exact gap** (1.72x vs `exp`'s 3.02x) — carried from
   cycle 2's S5, still open (§5.1).
4. **Make the repair path honest under adversarial corpora**: `exp2` exact
   0.57x on the boundary corpus, `Fast/FullRange` 0.95x there against
   `Fast/Finite`'s 3.72x, and two rows where `Finite` is *slower* than
   `FullRange` (§5.3).
5. **Spend the accumulated precision headroom or document it**: `pow`'s
   extreme corpus still asserts 8 with 5 measured (carried), and the
   README's "asinh and pow are within 8" sentence predates the cycle-2
   `asinh` rework (§6).

## 2. Contracts that must not change

Carried over verbatim from the last two cycles; they remain hard:

- `BitExact` matches the platform bit-for-bit, including signed zero,
  infinities, NaN payloads, and FMA placement read from disassembly — not
  source-level equivalence.
- Every `Fast` bound is asserted in `tests/accuracy.rs`, quoted identically
  in the kernel doc and README, and may only be tightened after a measured
  campaign (30M+ samples for `f64`, exhaustive for `f32`).
- `FullRange` is correct for all inputs; `Finite` skips checks only inside
  its documented domain.
- Tables and coefficients are generated by `tools/` from pinned upstream
  commits (cycle 2 closed the pinning gap); regeneration is byte-identical.
- Rare lanes are repaired by `reference/` through `patch_lanes`; the vector
  main path never owns the hard cases.
- A kernel whose acceptance test is `lb == ub` (correctly-rounded fast path
  with rounding-boundary rejection) keeps its full-corpus bit-exact test so
  a platform drift fails loudly — the equivalence is a property of glibc
  2.43, not of the algorithm.
- Acceptance evidence is end-to-end (`examples/bench.rs` rows via
  `tools/bench_matrix.py`), not microbenchmarks — with one amendment this
  cycle: the `traversal.csv` identity ladder and `repair.csv` density curve
  are admissible *diagnostic* evidence (they attribute cost), never
  *acceptance* evidence (only the function rows accept a change).

## 5. Speed workstreams

### 5.1 S1: explain, then close, the `exp2` exact gap — P1, small to diagnose

Carried from cycle 2 (its S5 diagnosis never happened). `exp2` exact 1.72x
vs `exp` 3.02x, same 128-entry table family, same schedule shape — and
`exp2`'s reduction is *simpler* (`x` is already in log2 units; there is no
`INVLN2N` multiply and no two-constant `NEGLN2` reduction). The gap being
this direction demands an explanation. Hypotheses to test, in order:

1. **The no-FMA schedule.** glibc's `exp2` has no `_fma` ifunc variant
   (README documents this), so the ported schedule is the SSE2 build's:
   unfused multiply-adds, longer dependency chains. `exp` replays a fused
   schedule. Count the serial-chain difference in the two kernels
   (`src/kernels/double/exp.rs`) and check it against the measured ns/elem
   difference (1.01 vs 0.78).
2. **The per-lane table loop.** Both kernels share the per-lane index →
   `TAB` load loop (`exp.rs:82–95`); if `exp2`'s shorter arithmetic hides
   less of the loop's latency, the loop is a larger *fraction* for `exp2`.
   `perf annotate` on the bench binary attributes this directly.
3. **Scalar baseline asymmetry.** `exp2`'s scalar baseline is 1.62 ns vs
   `exp`'s 2.17 ns — a faster denominator alone accounts for part of the
   ratio gap. Compute the comparison in ns/elem, not speedup, before
   concluding anything.

Acceptance: an explanation written into `exp.rs`'s module doc (the surface
the next cycle reads), plus any landed fix clearing ≥ 5% on the `exp2`
row with `exp`/`exp10`/`pow` unchanged (shared-primitive threshold) and
all exactness suites green. "Explained, nothing recoverable" is a valid
close — but it must be on record this time.

### 5.2 S2: the Exact-group large-buffer deficit — P1, medium

`floor`/`round`/`trunc`/`sqrt` exact at 1 M: 0.64–0.73x. The same rows at
4096: 1.00–1.08x (`round` 0.79x). The vector body is one instruction
(`round` two), so the deficit lives in traversal, not arithmetic — and only
in the memory-bound regime. The scalar baseline loop auto-vectorises for
exactly these functions (LLVM handles `floor`/`sqrt` intrinsics), so parity
is the honest ceiling; below-parity means `eval_slice` costs bandwidth or
overhead the plain loop does not.

Diagnosis first, on the Phase-0 dispersion data:

1. Extend the `traversal.csv` identity ladder to 1 M elements (it stops at
   65 K today) and compare its ns/elem against the cheap rows' deficit
   (~0.13 ns/elem for `floor`). If the identity ladder shows the same gap,
   the kernel is exonerated and the cost is pure traversal.
2. `perf` the 1 M `floor` case: look for bounds checks, chunk-boundary
   spills, or a scalar tail loop that defeats write-combining; compare the
   generated loop against the baseline's auto-vectorised one (`objdump`).
3. Check whether the baseline loop gets non-temporal or better-pipelined
   stores at 1 M that `eval_slice`'s chunked structure prevents.

Fix candidates (only after the diagnosis names one): flattening the
chunk loop for single-instruction kernels, hoisting the slice bounds
checks, or an `eval_slice` fast path when `LANES` divides the length.
`trunc` exact/F 0.42x is triaged under §5.3 first (it is a policy-wiring
smell, not a traversal one).

Acceptance: all four exact rows ≥ 0.95x at 4096 *and* 1 M (in-domain),
no other row worse than 3% — or a Documented Accept in the README's
"`sqrt` gains nothing" paragraph extended with the honest large-buffer
number and the reason. Either way the README's `sqrt` 1.00x claim is
replaced by a measured, annotated one.

### 5.3 S3: repair-path cost on adversarial corpora, and the `Finite` inversions — P2, medium

Three related symptoms, one suspect surface (`patch_lanes` /
`dispatch` in `src/kernels/mod.rs` and the per-kernel rejection masks):

1. **`exp2` on the boundary corpus**: exact 0.57x, `Fast/FullRange` 0.95x
   vs `Fast/Finite` 3.72x. The corpus straddles the subnormal/overflow
   edges, so the rejection mask fires per vector and the scalar repair
   dominates. `repair.csv` already shows `exp`'s 3.5x density cliff
   (0.80 → 2.77 ns/elem) while `erf`'s curve is flat — so a flat curve is
   achievable. Diagnose what `erf`'s rejection path does differently
   (its accurate path is also scalar per rejected lane), then either:
   batch the rejected lanes (collect-indices-then-loop instead of
   per-lane branch inside the vector loop), widen `exp2`'s main-path
   domain to cover the subnormal band the way cycle 1 did for
   `expf`/`exp2f`/`exp10f`'s `Fast` paths, or accept with the boundary
   number annotated in the README.
2. **`Finite` slower than `FullRange`**: `trunc` exact/F 0.42x vs exact
   0.64x (in-domain, 1 M); `round` exact/F 0.41x on mixed-special. By
   construction `Finite` does strictly less work, so these are wiring
   bugs or measurement noise — nothing else can explain them. Phase 0's
   dispersion data decides which; if real, trace the policy dispatch for
   these two kernels (`policy.rs`, `function_defs.rs`) before touching
   anything.
3. **Extend the `bench_matrix.py` inversion diagnostics** (landed in
   `1b2d243` for exact > fast) to also flag `Finite` slower than
   `FullRange` beyond the noise band, so this class of bug fails loudly
   in every future run.

Acceptance: `exp2` boundary-corpus exact within 15% of its in-domain
ratio or a corpus-annotated Documented Accept; the two `Finite`
inversions either reproduced-and-fixed or attributed to noise on record;
the new diagnostic committed. Bits must not change anywhere — this
workstream touches traversal and policy wiring only.

### 5.4 S4: family asymmetries — diagnose only, then decide — P3, small

Three rows where a sibling comparison suggests recoverable cost. For each,
the deliverable is a *diagnosis on record*; fixes are separate, gated
decisions:

1. **`cosh` 1.64x vs `sinh` 3.58x.** `cosh`'s scalar baseline (3.12 ns) is
   the family's cheapest, so the ratio may be denominator-driven. But the
   kernel (`hyper.rs::cosh::bit_exact`) also pays `half / e` — a full
   vector division — on every call, plus a conditionally-evaluated
   `expm1_exact` band. Compare ns/elem against `sinh`'s and attribute.
2. **`atan2` 1.58x in-domain vs 2.74–3.03x on the default corpus.** Find
   which band the in-domain corpus concentrates in
   (`invtrig.rs`), and either annotate the README row or, if one band's
   per-lane work dominates, treat it as a §5-style vectorisation candidate
   for cycle 4.
3. **`erfc` 3.13x in-domain vs 8.65x coherent.** Measure the accurate-path
   rejection rate per corpus (the CORE-MATH `lb != ub` rate). If the
   in-domain corpus lands disproportionately in the double-double slow
   path, that is the same corpus-honesty story as cycle 2's S4 — annotate,
   don't chase.

Acceptance: each of the three has an attribution in its module doc or
ROADMAP §6a. Any fix proposal graduates to a measured, separately-gated
change; nothing lands under this workstream itself.

### 5.5 S5: `acosh` coherent-corpus regression — P2, small

The S1 kernel measures 1.90x in-domain but **0.82x on the coherent
corpus** — below parity on exactly the adversarial-corpus gate cycle 2's
protocol prescribed for it (`atanh` shows the same shape milder: 1.40x vs
3.54x; `expm1` 1.77x vs 3.56x). The coherent corpus concentrates every
lane in one band, so the unconditional-evaluate-and-blend idiom pays for
all bands while the scalar baseline pays for one, hot in cache.

1. Confirm which band the coherent corpus lands in and reproduce the row
   outside the bench (perf-annotated) to see where the time goes.
2. Decide the stance explicitly: a band-uniform bypass (the `atan` idiom —
   but cycle 2 showed that idiom can turn into a corpus artifact, so it
   must be measured on *both* corpora and priced on the incoherent one),
   or a Documented Accept stating that band-coherent buffers are the
   kernel's worst case, with the number in the module doc.

Acceptance: coherent-corpus `acosh` exact ≥ 1.0x at ≤ 3% in-domain cost —
or the documented accept. Either way the corpus-duality table in the
README/ROADMAP quotes both numbers.

### 5.6 S6: f32 `Fast` exponentials stance — P3, small, carried unchanged

`expf` 2.23x/2.16x, `exp2f` 2.12x/2.14x (an inversion, within noise),
`exp10f` 2.48x/2.19x — `Fast` still buys almost nothing over exact, and
the ambiguity cycle 2 called unacceptable is still undocumented (only
`erfc.rs` has the considered-stance doc). Same two outcomes as before:
document the `erfcf`-style stance ("exact port already vector and cheap;
no cheaper approximation worth having") in each module doc, or prototype a
table-free single-polynomial path and accept only at ≥ 1.5x over exact
with a ≤ 4 ulp exhaustive bound. The documentation outcome is fully
acceptable and takes an hour; pick it unless the prototype is genuinely
wanted.

## 7. Measurement protocol

Unchanged from cycle 2 (§7 there), with three amendments:

- **Per-row dispersion is now data.** Phase 0.4 records it for the cheap
  rows; any accept/reject on those rows uses the row's own dispersion
  band, not the global 3% rule. A claimed win inside the band is not a
  win.
- **Corpus duality is now a five-corpus grid.** Any kernel with a
  data-dependent branch is gated on the corpus adversarial to that branch:
  coherent for band-blend kernels (§5.5's lesson), boundary for
  repair-path changes (§5.3), in-domain for everything quoting a headline
  number.
- **ns/elem before speedup.** Two of this cycle's anomalies (`exp2` §5.1,
  `cosh` §5.4) may be baseline-denominator effects. Every diagnosis states
  its comparison in ns/elem first; speedup is for the README.

Acceptance thresholds carry over: ≥ 10% on the targeted row (≥ 5% for a
shared primitive), no unrelated row worse than 3% (or its dispersion band
if wider), correctness suites green at every width, f32 changes
exhaustive.
